The idea

Make the opaque machine visible

  • eBPF's verifier is famously hard to reason about, and its bytecode executes somewhere you can't watch — deep in the kernel.
  • So instead of running eBPF in the kernel, this project reimplements the machine in Rust and compiles it to WebAssembly.
  • Programs assemble, verify and execute entirely client-side — every register, every stack byte, every step on screen.
  • No Docker, no Linux, no server. It even runs natively on a Mac.
  • A learning tool for exactly the thing that's normally invisible.

Four components, one Rust crate. The browser never leaves the page.

Component 1 · the assembler

A friendly assembly dialect

; sum the packet bytes
        mov r0, 0
        add r2, r1        ; end ptr
loop:   jge r1, r2, done
        ldxb r3, [r1+0]
        add r0, r3
        add r1, 1
        ja loop
done:   exit
  • Two passes: collect labels, then emit — so forward jumps just work.
  • Labels, comments (; # //), and the kernel-doc mnemonic names.
  • Full ALU (64- and 32-bit), lddw, every load/store width, all conditional jumps, call, exit.
Component 2 · the verifier-lite

The kernel's gatekeeper, in miniature

  • Writes to r10, the read-only frame pointer.
  • Jumps that land out of bounds — or in the middle of an lddw.
  • Division by zero, unknown helper ids, out-of-range shifts.
  • A program with no exit, or one that can fall off the end.
diagnostics, inline at the offending instruction
error@0: r10 is the read-only frame pointer
error@1: jump target 101 out of bounds
error@2: division by zero immediate
error@3: unknown helper function 77
warn @7: shift amount 40 outside 0–63
Component 3 · the interpreter

A real machine, stepped one instruction at a time

  • Registers r0–r10, 64-bit, r10 the read-only frame pointer.
  • A 512-byte stack below r10 and an editable packet at r1/r2 — every access bounds-checked with an explaining error.
  • Spec-correct semantics: 32-bit ops zero-extend; div/mod by zero yield 0 / unchanged.
  • Two log helpers that clobber r1–r5 like the real ones; a 100k-instruction budget.

What you see

Six panels that move together

  • An editor with five worked examples — packet summing, Fibonacci, stack spills, helpers, and a tour of programs the verifier rejects.
  • A live bytecode listing with hex encodings and diagnostics pinned to each slot.
  • Registers (hex + decimal + ABI role), a stack hex-dump, the current instruction, and a helper log — the changed register and the exact bytes written light up on every step.
  • Step, play at an adjustable speed, or run to end — with an exit-status pill.

Engineering notes

Small details that matter

  • The whole machine is one crate. Assembler, verifier, disassembler and interpreter share the ISA definition — the disassembler is reused to render every executed instruction.
  • 64-bit truth across the boundary. eBPF registers are u64, but a JS number only holds 53 bits — so register values cross into the browser as hex strings and the UI derives decimal with BigInt.
  • Native, browser-free tests. The interpreter and assembler are tested with plain cargo test — 8 cases covering loops, stack round-trips, signed compares and every error path.
  • Runs anywhere. Because the eBPF machine is the WASM module, there's nothing Linux-specific to install.

Run it

One command

# the machine is the WASM module —
# no Docker, no Linux needed
cd web && pnpm install && pnpm dev
# → http://localhost:5174

# rebuild the VM after editing vm/
wasm-pack build vm --target web \
  --release --no-pack \
  --out-dir ../web/src/lib/ebpf-vm
  • Pick an example, hit step, and watch the registers and stack change.
  • Un-comment a line in the "why verifiers exist" example to see a diagnostic appear.
  • cd vm && cargo test runs the interpreter suite natively.
